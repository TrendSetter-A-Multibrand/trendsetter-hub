# План модуля «Закупки / Отборки» — как определять, что покупать

Автор: `lead` (2026-10-05) по чтению дашборда и файлов в `WORK/`. Выводы про «как работает сейчас» — со слов агента по коду и файлам, в ходе сессии лично не перепроверялись; сверить с байерами. Цены и лимиты Claude API не оценивались — только «проверить».

## 1. Как отбор работает сейчас (факты со слов lead)
- В дашборде **нет механизма, который решает, что закупать**. «Отборки» — учёт уже сделанного выбора: байер сам заполняет Excel «Шаблон для офера» (лист «Отборка», 44+ колонки), дашборд его разбирает и сверяет приход/брак/отгрузки. Прайс поставщика дашборд не читает.
- **Отказы по строкам не хранятся**: в истории (~220 тыс. строк) только выбранные позиции; единственный «отказ» — статус на уровне всего оффера. Проверить систему по базе дашборда нельзя — нужны **пары файлов «прайс → итоговая отборка»**.
- **По Celio решение принималось по лоту целиком** (79 063 шт. в прайсе = 79 063 в отборке; 831 из 9 561 позиций с отрицательной прибылью всё равно взяли). По строкам делают проверку повторов с прошлыми лотами и разделение магазин/WB. → **главный вопрос байерам: решаете по лоту или по строкам** (от ответа зависит смысл колонок «Закупать» и «Количество»).
- Сегодняшняя «модель оценки» — **Excel-расчёт экономики строки для WB** (закупка = РРЦ×0,13; себестоимость ≈ (цена EUR×1,38+0,5)×курс; средний чек категории WB с листа «Ср чек»; комиссия WB 36%; НДС; маркетинг 6%; инвесторам себестоимость×1,2; опер.расходы 18%; налог 3,6% → чистая прибыль и наценка). Коэффициенты правят вручную от файла к файлу, в шапке файла они расходятся с формулами. Единого документа правил нет.
- Уже существуют справочники (Claude не нужен): классификатор (892 строки: отдел→категория→подкатегория→товарная группа + «Сезонность» и «Макс SKU на магазин»), словари категорий/сезонов/цветов/размеров.
- Данные о продажах: розница Ереван (недельные продажи, остатки, IMU; детализация пол/категория/группа/бренд, не артикул); WB — в выгрузках только остатки, продаж нет; Москва — не найдено.

## 2. Как решать «купить / отказать / сколько»
**(а) Правила без Claude:**
1. Жёсткие фильтры (ответ «Нет» + код причины): запрет бренда/канала; сезон не совпадает с окном продаж (сезонность группы + срок доставки); повтор уже закупленного артикула; нет обязательных данных.
2. Экономика строки (формулы байеров, коэффициенты в настройках, не в коде) → прибыль и наценка на штуку.
3. Оценка спроса по категории (пол × группа × канал): темп продаж, доля проданного, покрытие остатком в неделях.
4. Решение: «Да» если прибыль ≥ порога и покрытие < целевого; «Под вопросом» на границе; иначе «Нет» (пороги согласовать с байерами).
5. Количество = min(предложено поставщиком; темп × горизонт − остаток − в пути; «Макс SKU на магазин» × магазины + доля WB), затем деление по размерам по исторической доле.
6. Если решение по лоту: итог по лоту — прибыль, доля «плохих» позиций, неходовой остаток, максимальная цена, при которой лот окупается.

**(б) Где нужен Claude API, а где нет.** *Не нужен:* знакомые колонки поставщика (сохранённый маппинг), числа/валюта/курс, словарные размеры/цвета/сезоны, вся экономика, решение, количество, поиск повторов. *Нужен:* (1) новый формат прайса — Claude предлагает, какая колонка что значит, байер подтверждает, маппинг сохраняется; (2) категории/названия вне словаря — Claude выбирает из закрытого списка классификатора, байер подтверждает (отправлять уникальные значения, не строки: в примере 56 643 строки = 57 «семейств», 32 нужно разобрать); (3) текст «Почему» по уже посчитанным фактам (по категории, не по каждой строке; при сбое — шаблон); (4) позже — «грязные» файлы и PDF. Claude **не решает** «брать/количество».

**(в) Обратная связь.** В выходе у каждой строки/категории: «Рекомендация», «Решение байера», «Кол-во байера», «Причина правки» (короткий список + комментарий). Хаб хранит обе версии. Обучение — сначала без ML: подтверждённые маппинги/категории пополняют словари, раз в месяц разбор статистики правок и пересмотр порогов. Модель на истории — когда накопятся сотни решений с отказами.

## 3. Какие данные нужны и откуда (хаб не читает базу дашборда; способ попадания — загрузка файла / API / регулярная выгрузка)
Прайс поставщика (xlsx, десятки форматов, 50–120 тыс. строк) · классификатор и словари (листы шаблонов, могут расходиться) · продажи розницы Ереван (сводная, нужна плоская) · **продажи WB (API — проверить; временно лист «Ср чек» неизвестного источника)** · остатки WB/розницы · продажи и остатки Москвы (не найдено) · себестоимость (выгрузка из дашборда/1С; временно формула) · «уже закуплено/в пути» · курсы EUR/RUB, EUR/AMD (ЦБ) · коэффициенты WB (из Excel байеров в настройки) · сроки логистики · цены конкурентов — источника нет, не в первой версии · 1С — есть ли продажи/остатки по артикулам.

## 4. Что собрать у байеров
**Материалы:** (1) прайсы/лоты 3–5 поставщиков (Celio, Network360/COS, H&M, Новая Мода, DeadStock) **плюс итоговая отборка по каждому**; (2) 1–2 оффера с отказом и с частичным отказом, с причиной; (3) свежий Excel с экономикой и действующие коэффициенты (1,33 или 1,38+0,5; 0,06 или 0,07; 1,2 или 1,22) и кто их утверждает; (4) откуда лист «Ср чек» и как обновляется; (5) отчёты продаж: розница Ереван, Москва, WB за прошлые сезоны.
**Вопросы:** 1) решаете по лоту или по строкам, у каких поставщиков как; 2) сколько прайсов в месяц, размер, сколько времени на один; 3) что смотрите первым, какие пороги (мин. наценка/прибыль, макс. цена, покрытие в неделях); 4) исключения: «никогда/всегда берём» (бренды, категории, размеры, страны, каналы); 5) как считаете количество и делите магазин/WB, Ереван/Москва; 6) какие размеры убираете; 7) за сколько недель до сезона товар должен приехать; 8) что делаете с повторами артикулов; 9) 10–20 примеров «хороших» и «плохих» решений прошлых сезонов (что распродалось, что зависло); 10) какой формат выхода удобнее: файл поставщика + 3 колонки или «Шаблон для офера».

## 7. ТЗ первого шага (ТОЛЬКО после явного «да» пользователя): Этап 1 — библиотека разбора прайса
Файлы только в `backend/app/modules/purchasing/pipeline/` (`schema.py`, `headers.py`, `reader.py`, `normalize.py`, `report.py`, `cli.py`), `backend/app/modules/purchasing/tests/` и `backend/requirements.txt` (pandas, openpyxl, python-calamine, pytest). - Схема строки: `supplier_article`, `supplier_color`, `supplier_size`, `ean`, `brand`, `item_name_supplier`, `category_supplier`, `subcategory_supplier`, `gender_supplier`, `season_supplier`, `qty`, `rrp`, `client_price`, `currency`, `composition`, `photo_url`, `source_row`. Обязательно: `supplier_article`, `qty` и одна из цен.
- Словарь синонимов заголовков (без учёта регистра/пробелов/переносов): англ./рус. «Шаблона для офера», французские заголовки Celio, заголовки отборки Celio; дубль-заголовок → первое совпадение слева + предупреждение.
- Только `.xlsx` через calamine, значения формул из кэша; лист — с наибольшим числом распознанных заголовков; строка заголовков — в первых 10 строках (≥4 колонок; двойной заголовок англ./рус. учитывать); без поячеечного цикла по DataFrame (120 тыс. × 20 колонок — замерить время).
- Нормализация: артикулы/EAN/размеры как текст (ведущие нули сохранить, `116154302.0` → `'116154302'`), запятая в числах, `#N/A`/`#NAME?`/`#VALUE!`/nan → пусто с подсчётом, пустые строки пропускать (в т.ч. посреди данных), `qty` целое (отрицательное — предупреждение); справочники категорий/сезонов на этом этапе не применять.
- `parse_price(path) -> ParseResult` (лист, строки заголовков, `column_map`, нераспознанные колонки, недостающие обязательные, строки, статистика, предупреждения); понятная ошибка по-русски, если обязательных полей нет; строки молча не теряются. `cli.py` печатает отчёт (лист, соответствие колонок, нераспознанное, статистика, 5 первых строк).
- Тесты (pytest, фикстуры генерируются кодом с вымышленными значениями): шаблон с двумя рядами заголовков; один ряд; мусор над заголовком; французский Celio, лист не первый; артикулы с ведущими нулями и числовой; `#N/A` в цене; пустые строки посреди данных; нет колонки количества → ошибка с перечнем найденного; `.xls` → ошибка формата; дубль-заголовок → предупреждение; 120 000 строк (замер времени).
- Критерии приёмки: изменения только в перечисленных путях; нет FastAPI/SQLAlchemy/Alembic/сети/Anthropic и импортов из дашборда; нет реальных файлов/цен/секретов; pytest зелёный (все 11 сценариев); число строк на выходе + пропущенные пустые = числу строк данных; сообщения об ошибках на русском; нет кода «на вырост».
