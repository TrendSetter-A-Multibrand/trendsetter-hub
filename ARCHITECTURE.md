# ARCHITECTURE.md — Единая платформа инструментов (хаб + модули)

Статус: **черновик архитектуры, код не написан.** Источник концепции: `Платформа_инструментов_презентация.pdf` (сентябрь 2026). ТЗ подготовлено агентом `lead` (2026-10-01).
Пункты со статусом **[допущение]** и **[вопрос Qn]** не подтверждены пользователем — не считать их решёнными (см. раздел 9).

## 1. Идея

Один веб-хаб для всех отделов компании (Россия и Армения, один URL). Хаб — общее ядро; каждый отдел — модуль.

Общее ядро (не копируется в модули):
- роли и доступ по отделам;
- единый загрузчик файлов;
- очередь фоновых задач и статус обработки;
- журнал «кто что запустил и с каким результатом».

| Модуль | Статус | Суть |
|---|---|---|
| Закупки | **MVP** | xlsx-прайс поставщика → скоринг → файл с колонками «Закупать (да/нет)», «Количество», «Почему» |
| WB-карточки | roadmap | автообрезка фото, описание и SEO по шаблону категории; сначала файл на выгрузку, WB API — позже |
| Аналитика / дайджест | roadmap | еженедельный сбор данных по сезону/трендам + LLM-суммаризация по категориям |
| Ценообразование | roadmap | рекомендации по цене на основе дайджеста; автовыставление (WB, электронные ценники) — позже |

### Принципы (из PDF)
1. **Человек принимает решение.** Платформа рекомендует и объясняет «почему», ничего не закупает и не выставляет сама.
2. **Модульность.** Новый отдел = новый модуль, подключённый к ядру, а не переделка платформы.
3. **Простой контракт.** Вход — файл, выход — файл или рекомендация.
4. **Общий каркас.** Роли, загрузка, очередь, журнал — в ядре, не в каждом модуле.

## 2. Стек (повторяет стек компании, см. `WORK/Procurement dashboard/purchasing_dashboard`)

- Backend: Python 3.13, FastAPI, SQLAlchemy 2, psycopg3 (`postgresql+psycopg`), Pydantic, Alembic, python-jose (JWT HS256), bcrypt, slowapi, python-multipart.
- Excel: pandas, openpyxl, python-calamine, xlsxwriter (как в purchasing_dashboard; ограничения openpyxl — см. T1).
- Frontend: React 19, Vite, antd 6, react-router 7, axios, **обычный JS (не TypeScript)**.
- БД: PostgreSQL (managed, DigitalOcean, кластер fra1). Новая инфраструктура не поднимается.
- Деплой: droplet + docker compose + nginx.

Почему так: команда стек знает, парсинг xlsx и auth переносятся из purchasing_dashboard. Альтернатива (TypeScript) не вводится, пока команда не попросит.

## 4. Контракт модуля

Backend (`app/core/registry.py`):
```python
@dataclass(frozen=True)
class ModuleManifest:
    id: str                          # "purchasing"
    title: str                       # "Закупки"
    status: str                      # "mvp" | "roadmap"
    permissions: list[str]           # ["purchasing.view", "purchasing.run"]
    router: APIRouter | None         # монтируется на /modules/{id}; None = roadmap-карточка
    job_handlers: dict[str, Callable]  # имена уникальны и начинаются с "{id}."
    icon: str | None = None

MODULES: list[ModuleManifest] = [...]
```

**Добавить модуль = папка в `modules/`, одна строка в `MODULES`, одна строка в `frontend/src/modules/registry.js`, миграция.** Ядро не правится. Автодискавери/entry points отвергнуты (магия, нет выигрыша при 4–6 модулях).

Поток данных модуля: принять `file_id`(ы) + параметры → `enqueue` задачи → обработчик пишет `jobs.result_file_id` и/или `jobs.result_json` → UI опрашивает `GET /core/jobs/{id}` каждые 2–3 с.

## 5. Модель данных ядра (схема `hub`) [допущение A2]

- `departments` (id, code, name, is_active) — **справочник в БД, отделы добавляются/меняются админом без деплоя** (стартовые: purchasing, wb, analytics, pricing)
- `module_departments` (module_id, department_id) — какому отделу принадлежит модуль (модуль определён в коде манифестом, привязка к отделам — в БД)
- `users` (id, email unique, full_name, hashed_password, is_active, access_level: `admin|superuser|employee|viewer`, created_at)
- `user_departments` (user_id, department_id) — отделы сотрудника (может быть несколько)
- `files` (id, storage_key, original_name, content_type, size, sha256, uploaded_by, module_id, created_at)
- `jobs` (id, module_id, type, status `queued|running|done|failed` с CHECK, params JSONB, input_file_ids JSONB, result_file_id, result_json JSONB, error, progress 0–100, attempts, created_by, created_at, started_at, finished_at, locked_by, locked_at); индекс `(status, created_at)`
- `audit_log` (id, user_id, action, module_id, job_id, details JSONB, created_at)

«Последние запуски» на главной = `jobs` JOIN `users`/`files`, отдельной таблицы `runs` нет. Таблицы модулей — только в его схеме (например, `hub_purchasing`).

Уровни доступа (решение пользователя; таблицы ролей/прав заменены на фиксированные уровни + отделы — проще):
| Уровень | Что может |
|---|---|
| `admin` (команда IT, 4 человека) | всё, что superuser, **плюс** раздача ролей, управление пользователями, отделами, привязкой модулей |
| `superuser` (руководитель компании или отдела) | запускать и менять во **всех** модулях, чтобы сделать работу в любом; без управления пользователями и ролями |
| `employee` | полный доступ (`run`) в модулях **своих** отделов; в остальных — только просмотр |
| `viewer` | видит **только интерфейс и структуру** модулей; файлы и результаты не видит (на старте; решение пользователя) |

Права вычисляются в `require_access(module_id, "view"|"run")` (зависимость FastAPI) из `access_level` + `user_departments` + `module_departments`. Право `view`/`run` — на уровне модуля, модули не знают о ролях. Фронт получает вычисленные права из `GET /core/me`.

**Группы доступа.** Три таблицы ядра без приставки: `access_groups` (id, name, уникальное без учёта регистра), `access_group_permissions` (group_id, module_id, permission `view|run|responsible`, одна строка на пару группа-модуль), `access_group_members` (group_id, user_id). Группы только расширяют права: итог = максимум из базового (уровень + отделы) и группового, порядок `none < structure < view < run`; `view` даёт не ниже `view`, `run` и `responsible` дают `run`; группа поднимает и `viewer` (Q-G1). `responsible` не попадает в `module_access`: это отдельный флаг `module_responsible: {module_id: bool}` в `GET /core/me` (admin/superuser автоматически не ответственные, Q-G2); для Склада ответственный проходит действия «по ПИН» без ПИН (Q-G3). Права читаются из БД на каждый запрос, в JWT не кладутся; фронт тихо обновляет `/core/me` при возврате на вкладку и раз в 60 с (Q-G5). Удаления групп нет (Q-G4), запрещающих прав нет (Q-G6). Управление — `/admin/groups` (только admin). Подробности — `docs/TZ-access-groups.md`.

## 6. Ключевые решения

| Тема | Решение | Почему / альтернатива |
|---|---|---|
| Миграции | **Alembic с первого дня**, запуск явной командой `alembic upgrade head` при деплое. Никакого `create_all` и DDL на старте | У модулей свои таблицы; `init_db()` с `ADD COLUMN IF NOT EXISTS` (конвенция purchasing_dashboard) не умеет удалять/переименовывать. [вопрос Q11] |
| Очередь | Таблица `jobs` в Postgres + отдельный процесс `worker`: `SELECT ... FOR UPDATE SKIP LOCKED`, poll 2 с; reaper возвращает зависшие `running` (>15 мин) в `queued`, пока `attempts < 3` | «Не поднимаем новую инфраструктуру» исключает Redis/Celery. `BackgroundTasks` отвергнуты: теряются при рестарте, нет статуса и ретраев. Проверить T4 |
| Файлы | Docker volume `/data/files/{yyyy}/{mm}/{uuid}`, метаданные в `files`, доступ через `core/files.py` | Как в purchasing_dashboard. Абстракция делает переход на DO Spaces дешёвым. Риск: нет бэкапа volume. [вопрос Q5] |
| Auth | email + пароль, JWT (HS256), bcrypt, регистрации нет (создаёт админ), rate-limit на login | Как в компании. SSO — по ответу на Q3 |
| LLM | `core/llm.py`: `complete(prompt, system, max_tokens)` с таймаутом, ретраем, логом токенов. **LLM только формулирует «Почему»**; решение «закупать/сколько» — детерминированные правила. Батчи; при ошибке LLM — шаблонный текст, задача не падает | Результат проверяем и не зависит от LLM. Провайдер — [вопрос Q8] |
| Навигация | **Меню сверху — вариант 2 из PDF** (решение пользователя). Пока модулей ≤5–6 — вкладки; дальше группировка по отделам/выпадающее «Ещё», чтобы не ломать модульность | PDF прямо предупреждает: вкладки удобны только пока модулей немного |
| Локализация | Пока только русский; все строки в `frontend/src/core/strings.js`, библиотека i18n не ставится | Армянский — по ответу на Q9 |
| Деплой | **Временно Vercel** (решение пользователя, платформа не окончательная). Ограничения Vercel для воркера/файлов — см. раздел 11 | Проверяет technical-analyst; постоянная платформа выберется позже |

## 7. Модуль «Закупки» (MVP)

1. **Вход:** байер загружает xlsx-прайс (позже — несколько файлов).
2. **Обработка (задача в очереди):** нормализация (маппинг колонок по поставщику) → скоринг по правилам (маржа, оборачиваемость, сезонность, история продаж) → LLM формулирует «Почему».
3. **Выход:** файл с колонками «Закупать (да/нет)», «Количество», «Почему». Формат (то же форматирование vs новый xlsx) — [вопрос Q12].
4. UI: выбор поставщика, «Загрузить прайс», статус задачи, таблица АРТИКУЛ / ТОВАР / ЦЕНА / ЗАКУПАТЬ / КОЛ-ВО / ПОЧЕМУ, «Скачать файл».

Скоринг — чистые функции в `pipeline/scoring.py`, юнит-тесты на фиксированных входах. Допущение A5: в purchasing_dashboard остатки (`procurement.stock`) агрегированы по категориям, не по артикулам — скоринг MVP может быть только по категориям. **Блокер этапа 1: Q6 (откуда маржа и история продаж).**

## 10. Безопасность и секреты

Урок purchasing_dashboard: полный DSN боевой БД с паролем `doadmin` лежал в `run_local.ps1` и `docker-compose.override.yml` (только `.gitignore` как защита, разработка шла на проде). В хабе иначе:
- Секреты не лежат в файлах репозитория вообще. На сервере — переменные окружения/секреты (DO App Platform secrets или `.env` вне репозитория с правами 600); локально — только `.env` для локального Postgres.
- Отдельный пользователь БД хаба с минимальными правами (только своя база/схемы), не `doadmin`; отдельные ключи Anthropic на хаб.
- Локальная разработка — только на локальном Postgres из compose; боевой DSN на машины разработчиков не выдаётся.
- Сканер секретов (gitleaks) как pre-commit-хук и в CI; в `.env.example` только плейсхолдеры.
- Приложение при старте падает, если `SECRET_KEY` пуст/дефолтный; пароли — bcrypt; rate-limit на login; HTTPS обязателен.
- Пароль `doadmin` из purchasing_dashboard стоит сменить (вне этого проекта, решает пользователь).
